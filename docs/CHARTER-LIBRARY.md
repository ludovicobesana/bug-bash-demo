# Charter library

Charters are missions, not scripts. They identify a risk and an intended learning outcome while leaving room for the participant to choose the next useful experiment.

## Checkout recovery

**Explore** the checkout under interrupted or unreliable conditions **to discover whether** a user can recover without inconsistent payment or order state.

Useful experiments may include delayed connectivity, refresh, back navigation, a second tab, retry, or switching device. The charter does not require every experiment.

## State consistency

**Explore** the checkout in multiple browser tabs and navigation paths **to discover whether** the same order and payment state is represented consistently across the user journey.

## Support perspective

**Explore** recovery messages after an uncertain payment result **to discover whether** a support agent can explain the next safe user action without relying on internal implementation knowledge.

## Accessible recovery

**Explore** checkout recovery with keyboard-only and assistive-technology interaction **to discover whether** an interrupted action remains understandable and actionable without visual inference.

## Charter quality check

Before using a charter, ask:

- Does it name a risk rather than a generic product area?
- Does it invite learning rather than prescribe clicks?
- Does it have at least one usable oracle or boundary?
- Does it avoid duplicating an already-covered automated scenario?
